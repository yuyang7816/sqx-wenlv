# 荣e游产品逻辑蓝图

> 文档版本：1.1｜整理依据：当前 uni-app 前端页面、路由、Mock 数据及现有交互

## 一、产品结论

### 1. 产品名称

荣e游。

### 2. 产品定位

荣e游是面向多个地区的文旅信息与服务平台，当前以荣昌区为首个运营地区。平台面向游客、本地居民、地区文旅管理方和地区内文旅商户，提供“到目的地之前查攻略、到目的地之后玩得顺”的一站式服务。

它不是单一的景区购票工具，也不是单纯的资讯展示站，而是由四类能力组成：

1. **目的地内容入口**：按地区展示景区、线路、活动、非遗文化、公告和城市故事。
2. **本地消费入口**：按地区展示卤鹅、非遗好店、推荐门店、酒店住宿和餐饮预约。
3. **在地出行工具**：地图导航、停车通行、公共交通、线路站点、时刻表和实时位置。
4. **智能服务入口**：统一搜索、AI 文旅助手、消息通知、个人订单和反馈。

### 3. 核心价值

对游客：降低目的地信息搜寻、路线规划、预约和到达成本。

对本地居民：提供周末休闲、餐饮消费、活动报名和城市公共服务。

对商家和景区：获得官方曝光、客流导入、预约管理和消费转化。

对文旅管理部门：统一发布权威内容，沉淀游客行为数据，支撑活动运营和公共服务改进。

### 4. 建议产品主张

**一部手机游目的地，吃得地道、玩得明白、出行方便。**

### 5. 平台层级模型

荣e游采用“平台—地区—文旅资源—地区内商户”的四级结构：

1. **平台**：荣e游统一提供用户端产品、地区切换、搜索、地图、消息、用户中心和平台规则。
2. **地区**：一个具体的文旅目的地，例如荣昌区、万州区或某个区县。用户可通过当前位置或手动选择地区切换内容范围。
3. **文旅资源**：地区下的景区、线路、活动、非遗项目、公交、停车场等公共或官方内容。
4. **地区内商户**：地区下独立经营的酒店、餐饮店、民宿、非遗体验店、文创店等。商户之间相互独立，不能跨地区默认归并为一个商户。

用户切换地区后，首页推荐、搜索结果、地图 POI、景区、酒店、餐饮、活动和线路均应切换到所选地区；用户当前位置只用于提供默认地区和附近推荐，不改变订单所属商户。

## 二、使用人群定位

### 1. 核心用户

| 用户 | 典型场景 | 核心需求 | 产品任务 |
|---|---|---|---|
| 外地短途游客 | 周末或节假日来荣昌 1-2 天 | 去哪里、怎么玩、住哪里、吃什么 | 景区/酒店/线路推荐，地图导航，预约和订单 |
| 亲子家庭游客 | 安陶、非遗、古镇文化体验 | 安全、轻松、适合孩子、可预约 | 亲子标签、活动报名、路线时长、停车和卫生间信息 |
| 文化兴趣游客 | 专程了解荣昌陶、夏布、卤鹅 | 权威文化内容、传承人和体验点 | 非遗名录、文化导览、非遗好店、体验预约 |
| 美食游客 | 专程品尝荣昌卤鹅 | 正宗门店、招牌菜、营业时间、位置 | 卤鹅商家列表、详情、电话、餐饮预约 |
| 本地居民 | 周末休闲、聚餐、参加活动 | 附近门店、活动、公共交通和停车 | 地图服务、活动清单、美食地图、消息 |

### 2. 次核心用户

1. 商务或探亲访客：关注交通便利、酒店、餐饮和快速决策。
2. 老年用户：关注大字号、电话咨询、路线清晰和线下可执行信息。
3. 摄影及自驾用户：关注打卡路线、停车场、导航和开放时间。

### 3. 平台运营角色

1. 平台运营方：维护平台基础配置、地区开通、平台公告、推荐位、规则和商户审核。
2. 地区文旅管理方：维护本地区官方公告、景区、非遗、活动和线路内容，审核本地区提交的内容。
3. 景区/场馆：维护开放时间、票务、预约名额、核销和咨询电话。
4. 酒店/商户：独立维护自己的房型或商品、库存、营业时间、服务规则、订单履约和核销；平台不替商户运营这些业务数据。
5. 客服人员：处理平台服务异常、用户反馈和平台侧投诉，并按规则协助联系对应商户。
6. 内容运营人员：维护平台或指定地区的 Banner、推荐位、专题、热门搜索和 AI 知识库。

## 三、用户核心任务

### 游客任务链

**发现目的地 → 产生兴趣 → 选择地区与资源 → 规划路线 → 预约/购买 → 到达导航 → 到店/入园核销 → 评价分享 → 再次访问**

### 居民任务链

**查看附近服务 → 筛选门店/活动 → 预约或到店 → 接收提醒 → 完成消费 → 收藏/反馈**

### 地区内商户任务链

**提交入驻 → 平台/地区审核 → 发布商户信息 → 用户查看或跳转服务 → 商户自行履约 → 商户处理售后 → 维护经营信息**

商户拥有独立经营边界。酒店商户自行管理房型、价格、库存、预订、入住和核销；餐饮商户自行管理菜品、营业时间和餐饮预约；非遗商户自行管理体验项目、名额和现场核销。荣e游只在约定范围内展示商户信息、提供跳转或接口承接，不替代商户后台。

## 四、信息架构

### 一级导航

当前底部导航为：

1. **首页**：搜索、Banner、十宫格、公告、推荐内容、AI 和美食地图入口。
2. **消息**：系统公告、预约结果、活动提醒、订单状态和客服消息。
3. **我的**：个人资料、订单、预约、收藏、足迹、优惠券、反馈和设置。

### 首页功能区

1. 搜索：景点、酒店、美食、公交、线路、门店。
2. Banner：活动、节庆、目的地专题和消费优惠。
3. 快捷入口：荣昌卤鹅、旅游景区、酒店住宿、美食地图、停车通行、活动、非遗、地图、公交、旅游线路。
4. 公告：官方通知和重要运营信息。
5. 推荐：热门、卤鹅、景区、酒店分类推荐。
6. 智能服务：AI 文旅助手。

## 五、完整业务逻辑

### 1. 首次进入与登录

1. 用户打开应用，展示首页；未登录用户可浏览公开内容。
2. 当用户执行收藏、预约、下单、评价、查看个人订单时，触发登录。
3. 登录方式建议支持微信授权登录和手机号验证码登录。
4. 首次登录补充昵称、手机号；手机号用于订单通知和售后联系。
5. 退出登录后保留本地浏览历史，清除个人订单、收藏等私有数据展示。

### 2. 内容浏览

1. 首页推荐内容按运营配置展示，不应永久依赖前端写死数据。
2. 列表支持分类、区域、价格、评分、距离、开放状态和综合排序。
3. 详情页统一包含：图片、名称、标签、地址、开放/营业时间、费用、服务说明、电话、导航、收藏和相关推荐。
4. 景区详情增加游玩时长、适合人群、预约规则、停车、卫生间、无障碍和实时提醒。
5. 酒店详情增加房型、入住/离店日期、房量、取消规则、早餐和停车说明。

### 3. 预约与订单

平台可提供统一的服务记录/订单入口，但每条记录必须归属一个地区和一个具体商户或官方资源。酒店住宿、餐饮预约、非遗体验和商品消费等业务的实际订单由对应商户系统或商户侧规则负责；荣e游是否承接支付、订单和核销，取决于该商户是否完成接口接入。

平台服务记录公共字段：记录号、地区 ID、商户 ID/资源 ID、业务类型、联系人、手机号、金额摘要、服务时间、创建时间、同步状态、跳转地址。只有平台实际承接交易的业务，才增加支付状态、核销码和退款信息。

订单状态建议：

**待提交 → 待支付 → 已支付/待履约 → 使用中 → 已完成**

异常状态：**已取消、已关闭、退款中、已退款、支付失败、商家拒绝**。

不同业务的履约边界：

1. 平台承接的门票/活动/线路：按平台订单规则生成二维码或核销码，按日期核销。
2. 酒店：酒店商户自行管理预订、入住、库存、取消和退款；平台只展示结果或接收商户接口同步的状态。
3. 餐饮预约：餐饮商户自行确认名额、修改、取消和到店完成；平台展示商户返回的预约状态。
4. 非遗体验：商户自行管理体验名额、集合、履约和现场核销；平台负责展示规则并提供入口。

### 4. 支付、优惠和退款

1. 平台承接交易时，费用明细必须区分原价、服务费、优惠券、活动优惠和实付金额。
2. 平台优惠券只适用于平台配置的业务；商户自行发放的优惠由商户负责说明和结算。
3. 平台承接支付的订单由平台发送支付结果和服务提醒；商户自有订单由商户负责通知，平台可同步消息。
4. 退款由实际收款和履约方按商户/平台规则处理，荣e游不得承诺无法控制的酒店或商户退款结果。
5. 平台仅记录自身处理的取消、退款或投诉动作；商户侧动作以商户系统返回结果为准。

### 5. 搜索与推荐

1. 统一搜索覆盖景区、酒店、美食、门店、线路和公交。
2. 搜索结果优先匹配名称，其次匹配地址、标签和关键词。
3. 无结果时提供热门搜索、AI 问答和反馈入口。
4. 推荐应结合用户位置、浏览、收藏、季节、活动热度和库存状态。
5. 推荐位需支持开始/结束时间、排序、投放范围和点击/转化统计。

### 6. 地图与交通

1. 地图提供景区、酒店、美食、非遗、停车场和公交站点 POI 图层。
2. POI 详情可查看地址、电话、营业状态，并跳转系统地图导航。
3. 公交展示线路列表、方向、首末班、站点和实时位置；数据异常时显示更新时间。
4. 停车展示停车场位置、剩余车位、收费规则和导航入口；无实时数据时不得伪装成实时状态。

### 7. AI 助手

1. 支持自然语言咨询：景点推荐、路线规划、美食、公交、停车、活动和预约规则。
2. AI 回复应引用平台内可验证的景区、线路、商家和公告数据，并提供可点击跳转。
3. 对营业时间、票价、公交实时位置等时效信息显示数据更新时间。
4. 无法确认时明确提示“以现场/官方最新信息为准”，不能编造电话、价格和库存。
5. 对话支持清空、历史记录、问题反馈和转人工客服。

## 七、当前代码现状判断

### 已有基础

1. 页面路由覆盖面较完整，首页和底部导航骨架已建立。
2. 景区、酒店、卤鹅、非遗、线路、活动、交通、地图、搜索和 AI 的信息架构已经成形。
3. 餐饮预约具备表单校验、记录列表、修改、取消和本地存储状态流转。
4. 景区详情具备收藏、电话和导航入口；首页具备下拉刷新和触底加载交互。

### 主要缺口

1. 多数页面使用 Mock 数据，`common/config.js` 仅预留本地 API 地址，尚未形成地区、商户和资源接口契约。
2. 首页、详情页和 AI 页面仍大量使用占位图片，影响目的地可信度和转化。
3. “我的订单”、收藏、足迹、优惠券、客服和设置目前多为未实现或“敬请期待”。
4. 预约体系存在餐饮预约记录，但缺少统一订单、支付、核销、退款和消息通知。
5. 搜索和公交结果中存在待接入标记，地图、停车和实时交通需要明确数据来源与更新时间。
6. 当前数据模型按页面分别维护，后续接后端前应统一平台、地区、商户、资源、服务记录和接口同步模型；酒店库存等商户经营数据不应默认纳入平台主数据。

## 八、指标体系

### 北极星指标

**有效文旅服务订单/预约完成数**：用户在平台完成预约、购票、住宿、活动报名或餐饮预约并实际履约的数量。

### 漏斗指标

1. 首页访问率、搜索使用率、列表点击率、详情到达率。
2. 收藏率、导航点击率、预约/下单发起率、支付成功率。
3. 核销率、完成率、取消率、退款率、评价率。
4. AI 使用率、AI 推荐点击率、AI 转人工率。
5. 活动曝光、报名、到场和复访转化。

### 服务质量指标

1. 景区/酒店/商家信息准确率和更新及时率。
2. 搜索无结果率、接口失败率、页面加载时长。
3. 客服响应时长、投诉解决时长和用户满意度。
4. 公交、停车和营业状态数据的新鲜度。

## 九、产品边界与原则

1. 荣e游负责平台能力、地区组织、商户入驻审核、信息展示、流量导入、预约/交易连接和服务提醒；不替代景区、酒店、商家自身的经营及履约管理系统。
